# Projects thread pane and Overview (dashboard)

A project's threads panel (right of the chat) opens on its Overview: a serif greeting ("Welcome, Ada." or "Welcome back, Ada." with a name in Settings, "Welcome back." without; see `settings-name` in `settings.md`) and the attention sentence, then the threads grouped by what they need from the person. Choosing a thread replaces the Overview in the panel with the thread's pane, at `/projects/:id/threads/:threadId`: header, pull request bar, transcript with live text and tool calls, the question a thread waits on, the box to steer it, and the files it changed. How it is built is in `docs/architecture/thread-pane.md`; the routes it calls are in `docs/THREADS.md` and `docs/SCHEDULING.md`.

Everything here starts an agent or opens a pull request, so it needs a stack seeded with `--fake-runtime`, started with the tripwire stubs and the fake `gh` first on `PATH`, and a bare origin for the fixture repo (see [Projects](./projects.md), "Thread worktrees and pull requests"). Never drive it against the real GitHub or the real CLIs. The recipes below were run against exactly that: the fake CLI, the fake `gh`, a real dashboard and a real host.

## Sub-features

- `thread-overview` shows the greeting and groups, in order, with Waiting on you and Resolved at 0 when empty, other empty groups hidden, and Resolved folded.
- `thread-senders` names who sent each message the thread got: the coordinator's brief and steers (with the person's quote), the person, a routine, AOP.
- `thread-transcript` opens a thread and follows its turn live: the person's message, the working row and its time, the live text, tool calls folded above each reply, no duplicates after a reload or a restart.
- `thread-answer` answers a waiting-on-you thread with an option and with free text.
- `thread-steer` steers a thread, stops it (button and Escape), and reads its steps and status line.
- `thread-limits` shows a queued thread (run cap 1) and a rate-limited one (countdown, Resume now on the pane and on the card).
- `thread-pr` opens a pull request from the bar, meets the honest `UNPUBLISHED_WORK` refusal, pushes and merges, and watches the thread settle.
- `thread-changes` shows the file the thread wrote in its worktree and sends review comments to the thread.
- `thread-manage` marks resolved, deletes with a confirmation, and shows usage.
- `thread-run-cap` changes the run cap in Settings and sees it take effect (also in [Settings](./settings.md)).

## How to get to it (user POV)

Open a project (the panel at the right is the Overview). Choose a row, or a thread chip or card in the chat: the address becomes `/projects/<id>/threads/<threadId>` and the panel shows the thread under a breadcrumb **Threads › title**; choosing **Threads** goes back. The thread's header is one 56px row: the breadcrumb and the title cut to one line (its full text is the tooltip; clicking it opens `thread-details`), then a resolve check (`thread-resolve-button`), expand, a `…` menu and close. There is no meta line and there are no tabs.

## Driving it with verify-stack and drive

Preconditions: a run seeded with `--fake-runtime`, the tripwire stubs and fake `gh` first on `PATH`, a bare origin (see above), `<api>` and `<repoId>` from `state.json`, a project created in the dialog and a new Claude in Chrome tab on `<dashboard>/`. Type coordinator messages into the Coordinator tab; the threads' own briefs carry the markers.

- **Spawn.** In the chat send `Start three. [fake: steps=1 delay=500 calls='[{"name":"thread_spawn","arguments":{"title":"Pick a database","prompt":"Choose [fake: ask=\"Which database?\" options=\"Postgres|SQLite\"]"}},{"name":"thread_spawn","arguments":{"title":"Add notes file","prompt":"Write notes [fake: steps=3 delay=2000 write=\"NOTES.md=hello from the thread\"]"}},{"name":"thread_spawn","arguments":{"title":"Slow refactor","prompt":"Refactor [fake: steps=4 delay=4000]"}}]' say="On it. Three threads."]`. Give every thread an explicit `title`: a marker in the title or brief is replayed on every turn.
- **Senders (`thread-senders`).** Have the coordinator start a thread with a quote and a long brief: `start it [fake: calls='[{"name":"thread_spawn","arguments":{"title":"Quoted","prompt":"<12 lines of text>","quote":"ship the login fix friday"}}]']`, and one without a quote. Open each: the first row is `user-message` with `data-sender=coordinator` on the left, `sent-message` with `data-brief=true` and `sent-message-sender` `Brief from the coordinator`; the quoted one has `forwarded-quote` reading `You said:` and the quote above the brief, the long brief is folded with `user-message-fold` `Show full brief` (it unfolds to `Show less`). Have the coordinator steer a thread (`thread_steer` with `message` and `quote`): a `Coordinator` card (no `data-brief`) with its quote; sent while the thread works, it is drawn inside the reply as `steered-message` with `data-sender=coordinator` and the same card. Type in the thread's composer: the person's bubble on the right, `data-sender=person`, no card. A routine with `target: "thread"` run with `POST <api>/api/projects/<id>/routines/<rid>/run`: the thread's brief reads `Brief from routine · <name>` on the right and shows the routine's own words. `thread_report` from the coordinator (`calls` with `thread_report`) lists each line with `from`. Older rows: set a thread's brief back to the shape older hosts stored (`update chat_messages set origin_json='{"type":"coordinator-relay","quote":null}' where id=...`), `delete from schema_migrations where version=26`, and `restart-server`: migration v26 marks it the brief again.
- **Overview (`thread-overview`).** In the panel's overview, `project-attention` has `data-waiting=1` (amber) and there is no counters row; a card shows its title, one status line, the steps ring or PR chip and the age, and no branch (the branch is `thread-branch` in the pull request bar above the steer box); `thread-group` elements appear in the order Waiting on you, Working (`data-status` = `waiting-on-you`, `working`), and each card is in its group. Later, with a rate-limited and a queued thread present, the order is Waiting on you, Working, Queued (oldest first, the order they will start), Rate limited, Ready for review, Landing, Idle, Resolved. Waiting on you and Resolved are drawn at 0 with their `thread-group-hint` ("Decisions, reviews, and permission requests." / "Completed threads."); other empty groups are not drawn. Click `thread-group-toggle` of Resolved: it opens; click another: it folds. Type in `thread-search`: every group opens and only matching cards stay, `thread-count` reads `N of M`.
- **Threads that do not load (`thread-overview`).** Make the host fail to list the threads by breaking one thread row in the run's scratch database: `sqlite3 <home>/projects.sqlite "update chat_sessions set target_json='{\"kind\":\"cloud\"}' where title='<thread title>'"`. `GET <api>/api/projects/<id>/threads` answers 500 (a ZodError in `logs/server.log`). The Overview shows `threads-error` reading `Could not load this project's threads: Request failed (500)` with `threads-retry`; a thread's address shows `Could not load this thread: …`, and each card in the Coordinator tab the same. Put `{"kind":"host"}` back: within a few seconds the page recovers by itself, with no click.
- **Transcript (`thread-transcript`).** Choose the `Pick a database` card. `thread-pane` shows `thread-title`; clicking it opens `thread-details` with `thread-status` `Waiting on you`, the repo name, the branch `aop/pick-a-database-<id6>`, `thread-usage` (`4,215 tokens · $0.01` for the fake), the brief as a `sent-message` card headed `Brief from the coordinator`, `1 tool call` folded in `work-log-summary` above the agent's reply. Steer an idle thread with `Think hard [fake: steps=6 delay=3000 say="Done thinking."]` (type in `composer-input`, check its value with `javascript_tool`, then press Return): the person's `user-message` shows at once, `thread-working` reads `Claude Code is working · 0s` and counts up, `work-log` for the running turn appears with `1 tool call · Bash` and grows. Reload the tab mid-turn: the message is there once, `thread-working` counts from the message's time, and `[...document.querySelectorAll('[data-message-id]')].map(e => e.dataset.messageId)` equals the ids in `GET <api>/api/threads/<id>/messages`. `bun $S/verify-stack.ts restart-server --name <run> --crash` mid-turn: the tab stays, `project-stream-state` returns to `Live`, the detached fake finishes and the pane settles on `Idle` with the same ids and the reply once.
- **Answer (`thread-answer`).** In the `Pick a database` thread `answer-card` shows the question, `answer-option` `Postgres` and `SQLite`, and a compact box. Click `Postgres`: the person's bubble reads `Postgres`, the status leaves `Waiting on you`, and the reply reads `Fake reply for turn 2 of session <id> (resumed)`: same runtime session (`chat_sessions.runtime_session_id` is unchanged). For free text, spawn `Naming [fake: ask=\"What should the new service be called?\"]` (no options): the card has only the box; type `billing-gateway`, press Return, and the same happens.
- **Steer and Stop (`thread-steer`).** While a turn runs `composer-stop` (with `Esc`) is shown, and `thread-stop` in `thread-menu`; click one, or press Escape in `composer-input`: the run is `cancelled` in `chat_runs`, `pgrep -f fake-cli.ts` finds nothing, the thread is `Idle`. For a thread that reports steps (`calls` with `aop_report_status`, see [Projects](./projects.md)) `thread-progress` (at the top of the transcript, inside `chat-scroll`, so it scrolls away with it and never covers a line) shows the line while it works and `thread-step` rows with `data-state` `done`, `active`, `pending`, and the ring reads `n/m`.
- **Limits (`thread-limits`).** Set the cap to 1 (see `thread-run-cap`) and send `Queue three.` with three `thread_spawn` calls whose briefs are `Run A [fake: steps=3 delay=3000]`, `Run B ...`, `Run C ...`. The Overview shows `Job A` Working and `Job B`, `Job C` in a Queued group reading `Waiting for a free run slot`, `Job B` first. Open `Job B`: `thread-notice-queued`, and `composer-stop` ends its wait (status `Idle`, it never runs). A brief with `[fake: ratelimit=120]` gives a Rate limited group whose card has `thread-card-resume`; its pane shows `thread-notice-rate-limited` with `thread-resume-countdown` counting down (`in 1m 43s`) and `thread-resume`. Click it (pane or card): the thread runs again in its session, ends `Idle`, and its reply reads `Your usage limit has reset. Continue with the task where you left off.`
- **Pull request (`thread-pr`).** In `Add notes file` (worktree holds `NOTES.md`), `pr-bar` shows the branch (`thread-branch`), `pr-bar-changes` `1 file changed`, `pr-open` ("Create PR"), a chevron for the draft, and the cross `pr-bar-hide`; the cross puts the bar away for the thread until `thread-show-pr-bar` in `thread-menu` brings it back. There is no bar for a rate-limited thread with no pull request, or one that changed nothing. Click it: it reads `Creating…` for about ten seconds (the fake writes the pull request text), then `pr-bar-chip` `PR #1`, `pr-sync`, `pr-merge`, the status `Ready for review`, and `calls.log` in `<home>/fake-gh` holds one `gh pr create`. Steer the thread with `Add more [fake: steps=2 delay=1200 write="MORE.md=extra work"]`, wait for `Idle`, click `pr-merge`: `pr-error` (`data-code=UNPUBLISHED_WORK`) reads `The thread has work its pull request does not include; open the pull request again to push it, then merge` and shows `pr-push-latest`. Click it: the toast `Pushed the latest changes to #1`, the error clears. Click `pr-merge` again: the toast `Merged the pull request`, `pr-bar-state` `Merged` (purple), the status `Resolved`, `thread-notice-resolved`, and the origin's `main` has the squash commit, the worktree and branch are gone (`git -C <repoPath> worktree list`, `branch`). Opening a pull request for a thread with nothing to publish, or merging while a turn runs, shows `NOTHING_TO_PUBLISH` and `THREAD_BUSY` the same way.
- **Changes (`thread-changes`).** Click `pr-bar-changes` (`1 file changed`): the pane's `data-view` is `changes` and it shows `thread-diff-file` for `NOTES.md` with `+1 −0`, its line `hello from the thread` in `thread-diff-line` (`data-line-type=add`). Hover a line and click its `diff-comment-button`, type a note, press Add (or Cmd+Enter): `review-queue-panel` shows the card and `review-send`. Click it: the pane returns to the conversation and the thread has a new user message beginning `Review comments on the current diff:`. The comment queue is kept in this browser (`localStorage["aop.thread-review-queue.<threadId>"]`).
- **Manage (`thread-manage`).** `thread-menu` then `thread-resolve` on an idle thread: status `Resolved`, worktree gone, branch kept. `thread-delete` shows a confirmation naming the thread; Cancel changes nothing (`GET <api>/api/threads/<id>` still 200), Delete returns to the project, the card is gone, `GET <api>/api/threads/<id>` answers 404 and the branch and worktree are gone. `thread-resolve` is disabled while a turn runs, waits, or a merge lands.
- **Run cap (`thread-run-cap`).** Open Settings (⌘, or `project-switcher-settings`), find `setting-max_concurrent_runs` under Runs, type `0`: `setting-error-max_concurrent_runs` reads `Enter a whole number from 1 to 32.` and `GET <api>/api/settings/max_concurrent_runs` still answers the old value after two seconds. Type `1`: within a second `GET` answers `"1"` and a batch of three threads runs one at a time.
- **Proof.** Screenshots of the Overview with every group, the pane in each state (working with the live row and tool calls, waiting with the answer card, queued, rate limited with the countdown, resolved and merged), the `UNPUBLISHED_WORK` refusal, the changes view, the confirmation dialog and the Settings error; the `messageId` lists before and after the reload and the crash; `GET <api>/api/threads/<id>` after each action; `read_console_messages` with `onlyErrors: true` after every flow. State that the runtime was the fake CLI and GitHub was the fake `gh`.

## Gotchas

- Screenshots from the Claude in Chrome tab crop the right and bottom edges. Scale the page first, then click: `document.getElementById('root').style.transform = 'scale(0.9)'; document.getElementById('root').style.transformOrigin = 'top left'`. Do it after every reload, and before you click a field near the bottom edge (the composer): a click on a ref that is partly outside the visible part of the tab focuses nothing, and the typed text is lost.
- A tab that is not in front reports `document.visibilityState` as `hidden` and types slowly. Read `composer-input`'s value with `javascript_tool` before pressing Return, or the message is sent short or not at all. A hidden tab also does not mark a thread read (the pane marks it read only while the page is visible).
- Type ASCII only into the boxes. A `·` or another non-ASCII character in a `type` call left the composer in a state that swallowed every later keystroke until the page was reloaded, and a message that fails to appear with no error is usually text that never reached the box: read its length first. If keystrokes stop landing, reload the tab (clear `localStorage` keys starting `aop:draft` for a stale draft).
- The gutter button of a diff line (`diff-comment-button`) is 14 px wide and shows only on hover, so a pointer click through the tool can miss it. Open the editor with `javascript_tool` (`document.querySelector('[data-testid=diff-comment-button]').click()`), then type the note in the editor's box, press Cmd+Enter, and click `review-send` for real.
- The Bun dev server hot-reloads on any source edit. While files under `apps/dashboard/src` change (another agent, an editor), a page you are typing in reloads and loses its text.
- The brief of a thread with a `[fake: ...]` marker is replayed by the fake on every turn, including the turn that writes its pull request text, so opening a pull request takes as long as the brief's script. Give such a thread a short script.
- The PR bar's `Merge` is enabled only for an open pull request; a thread with no repository has no bar and no changes view.
- A file the thread wrote and has not committed (fake `write=` files are, until the pull request opens) shows its real `+N −0` on the folded row, before it is opened: the host counts untracked files when it lists them. Only an untracked text file over 1 MiB shows `+0 −0` until it is opened. To see folded rows, write twelve or more files so they start folded, or click `Collapse all` in the Changes header (it has no test id and shows with two or more files). `thread-diff-fold-collapse` folds unchanged lines inside a hunk, not files.
