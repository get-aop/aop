# Project settings, memory, usage and Devices

A project's settings are a dialog over the project screen at `/projects/:id/settings`, in nine sections with a left nav in three groups: General, Models, Threads & permissions, Computer use, Notifications; then Environment, Memory, Usage; then Advanced. Each section has a heading and one line about it. Every setting saves as it changes (choices at once, text once typing pauses for 600 ms or the field loses focus, and on leaving the section), and its row says `Saving…`, then `Saved`, or the host's refusal; there is no Save button. × and Escape close it back to the screen it opened over (the project home for a deep link), and the chat underneath keeps its draft. Below `md` it is a full-screen sheet with the nav as a row of icon tabs that scrolls sideways. Arrow keys, Home and End move between the nav's sections. The host owner also has a **Devices** section in the app's Settings dialog, for pairing and revoking devices. This map covers both. The host-level dialog (General, Repositories, Runtimes, About) is in [Settings](./settings.md).

Everything that runs an agent needs a stack seeded with `--fake-runtime` and started with the tripwire stubs first on `PATH` (see [Projects shell](./projects-shell.md)). Usage needs at least one finished turn; the Devices check needs the built dashboard bound to the network (recipe `shell-pairing` there).

## Sub-features

- `psettings-general` is name and icon, then goal (`n / 8,000`) and instructions (`n / 16,000`) under "What agents are told".
- `psettings-models` is a Coordinator group and a Threads group, each a model and an effort (each with a default choice that reads `Default (<model>)` once a run of the role on default reported its model, plain `Default` before).
- `psettings-threads` is thread access under Permissions (new projects start on full access, which shows one amber note while selected; choosing it asks first; while the host skips permission checks the row shows only an "Overridden" note with a link that opens Settings › Runtimes), and fix pull requests automatically and auto-continue under Automation.
- `psettings-computer-use` and `psettings-notifications` are one row each (computer use keeps its CUA readiness box and setup guide; host owner only).
- `psettings-advanced` is Pause, Restart coordinator and Archive in one group, and Delete alone in a red-edged Danger zone.
- `psettings-memory` lists memory read-first (`MEMORY.md` under "Read every thread", topic files under "Memory files"), opens a file in an editor in place of the list (edit, create, delete), and sends "Tell Claude what to change or remove" to the coordinator, which edits the files with its memory tools.
- `psettings-environment` attaches and detaches repositories; detaching one a thread works in is refused with a message naming the thread.
- `psettings-usage` shows, per time window, threads, tokens, cache hit, code changes (+/− lines in the worktrees of the threads that ran in the window), coordinator share and cost; a stacked bar with its breakdown; the threads with a share bar, sortable by share, cache hit or recency; a copy button for a plain-text summary; and a per-model table only when several models ran.
- `psettings-devices` shows a pairing code with a countdown, lists paired devices, and revokes one. Only the host owner sees it.

## How to get to it (user POV)

- Open a project and choose **Settings** in its header, or `…` then **Settings**. The addresses are `/projects/:id/settings` (General), `/settings/models`, `/settings/threads`, `/settings/computer-use`, `/settings/notifications`, `/settings/environment`, `/settings/memory`, `/settings/usage` and `/settings/advanced`. `/settings/general` is not an address.
- Devices: choose **Settings** in the sidebar footer (or `⌘,`), then **Devices**. The entry is missing for a paired device.

## Driving it with verify-stack and drive

Preconditions:

- A run started with the tripwire on `PATH`, seeded with `--fake-runtime`, and a project made in the New project dialog with the seeded repo attached. For the Devices check start it as `shell-pairing` describes (`AOP_BIND_HOST=0.0.0.0`, `DASHBOARD_STATIC_PATH` on a fresh `bun run build:dashboard`) and open `http://127.0.0.1:<serverPort>/` for the owner.

- **General and autosave (`psettings-general`).** On `/projects/<id>/settings` change `settings-name`, `settings-goal` and `settings-instructions`: nothing is sent while typing, then within about a second the row's `settings-save-state` reads `Saved` and the header title changes. Type into a field and press Escape at once: the dialog closes and `curl -s <api>/api/projects/<id>` still has the new text. A blank name shows `settings-name-error` and is never sent. On `/settings/models` choose another thread model: it saves at once (`thread.model`, `thread.effort` in the API).
- **Thread access (`psettings-threads`).** A project created from the New project form starts on full access: `settings-thread-access` has `data-value="full-access"` and `settings-full-access-warning` is visible (the form itself shows `new-project-full-access-notice`). Choose Edit files (`settings-thread-access-auto-accept-edits`): it saves without a question, the note goes, the option says other commands are denied with no approval prompt, and the API reports `threadAccess: "auto-accept-edits"`. Choose Full access again: a question titled `Give threads full access?` opens before anything is saved; `confirm-dialog-confirm` saves it. Turn on Skip permission checks (`PUT <api>/api/settings/agent_cli_skip_permissions` `{"value":"true"}`) and reload: the row shows only `settings-thread-access-overridden`, and `settings-thread-access-runtimes` opens Settings on Runtimes over the project settings.
- **Use default passes no flag (`psettings-general`).** New projects start with the model on default and the effort on Low and High, so set all four selects to Default (each saves at once; `curl -s <api>/api/projects/<id>` shows `model` and `effort` null for both roles). The fake CLI's runtime configuration must list the models the settings offer, or an explicit choice falls back to the configuration's default model: `POST <api>/api/runtime-configuration/providers/<fake provider id>/models` with `{"description":"Opus 5 (fake)","model":"claude-opus-5","thinkingLevels":["low","medium","high","extra-high","max"]}` (the fake provider's model has no levels, so it takes no effort flag). Send the coordinator a message that starts a thread (`[fake: calls='[{"name":"thread_spawn","arguments":{"title":"Add notes","prompt":"Add it [fake: write=\"NOTES.md=hello\"]"}}]']`), then a second message and a message to the thread in its composer. Read what each launch really received: `jq '.launches[] | {turn, model, effort, flags}' <home>/fake-cli/sessions/claude/*.json` (the session ids are `chat_sessions.runtime_session_id`). Every launch has `model: null`, `effort: null` and no `--model` or `--effort` in `flags`, the resumed ones carry `--resume`, the thread's chips read `fake-claude` and `Default effort` once a thread run reported its model (`Default model` before), the settings' model selects read `Default (fake-claude)` and `curl -s <api>/api/projects/<id>` has `reportedRuntime.{coordinator,thread}.model` `fake-claude`, and Usage lists the model `fake-claude`. Then choose Opus 5 and an effort for both roles: the coordinator's next launch passes `--model claude-opus-5 --effort <effort>` (Extra is `xhigh`), a thread started after that passes them too, and a thread started before keeps passing none (its chips say so). Choose Default model and Default effort in the coordinator's composer chips: the next launch has no flag again. Usage now lists `fake-claude` and `claude-opus-5`.
- **Advanced (`psettings-advanced`).** `settings-pause` asks, then the header shows a `paused` tag and the button reads Resume; `settings-restart-coordinator` asks, then a toast reads `Coordinator restarted`; `settings-delete` asks, deletes and returns to `/`.
- **Memory (`psettings-memory`).** Open `/settings/memory`. The list shows `MEMORY.md` under Read every thread and topic files under Memory files; clicking a row opens the editor in place of the list and `memory-back` returns. Type `Remember the Friday deploy freeze [fake: calls='[{"name":"memory_write","arguments":{"name":"deploys.md","description":"Deploy rules","body":"No deploys on Fridays"}}]']` in `memory-request-input` and press Enter: `memory-request` goes to `working`, then `answered` with the fake reply in `memory-request-status`, and `deploys.md` appears in the list without a reload. Click `memory-new`, fill `memory-new-name` (`testing` becomes `testing.md`), `memory-description` and `memory-body`, click `memory-save`: the file is listed with its updated date and the API and `sqlite3 <home>/projects.sqlite "select name, body from memory_files"` show it. Edit the body and save; click `memory-delete` and confirm: the file is gone from the list, the API and the table.
- **A file the coordinator changes (`psettings-memory`).** Type into `memory-body` without saving, then `curl -s -X PUT <api>/api/projects/<id>/memory/testing.md -H 'content-type: application/json' -d '{"description":"x","body":"from the coordinator"}'`, then send the coordinator any message (`POST <api>/api/projects/<id>/messages`, `{"text":"hi"}`). Within about a second `memory-changed-notice` appears and the typed text is kept; `memory-load-newer` swaps in the host's copy. A hidden tab does not reload on focus (that trigger needs `document.visibilityState` to be `visible`); the message is the reliable trigger.
- **Environment (`psettings-environment`).** Register a second repository (`cp -R <run>/fixtures/repo <run>/fixtures/repo2`, then `curl -s -X POST <api>/api/repos -H 'content-type: application/json' -d '{"path":"<abs path of repo2>"}'`) and reload `/settings/environment`. Open `settings-repo-add` (Add): `settings-repo-add-menu` offers it as a `settings-repo-add-option`; picking it adds a row to `settings-repos-attached` and `GET <api>/api/projects/<id>` lists both ids. `settings-register-repo` (Register another repository…) opens the attach dialog; the repository it attaches is added to the project too. Start a thread in the first repository (`POST <api>/api/projects/<id>/threads` with `{"title":"Fix the login redirect","prompt":"go"}`), then click `settings-repo-detach` on that repository: the row shows `“Fix the login redirect” still works in repo. Stop and delete it first, then remove the repository.`, the network log shows `PATCH … 409`, and the repository stays attached. Any thread of the project in that repository blocks the detach, resolved ones too: the row names the unresolved threads that still work in it and, separately, counts the resolved ones that belong to it, which only deleting them (`DELETE <api>/api/threads/<id>`) lets go. Detaching the other one succeeds.
- **Usage (`psettings-usage`).** Give the project usage with the fake CLI: `POST <api>/api/projects/<id>/messages` with `{"text":"hi [fake: usage=10,5,200,4000]"}`, and a thread with `{"title":"t","prompt":"go [fake: usage=1000,200,3000,50000]"}`. Open `/settings/usage`: `usage-stat-tokens` reads the sum of the four buckets (the `usage-part-*` rows), `usage-stat-code-changes` reads the sum of the line counts in `GET <api>/api/threads/<id>/diff` over the threads with runs in the window (a `[fake: write="f.txt=hello"]` in a thread prompt makes one; a resolved thread whose worktree is gone adds nothing), `usage-stat-cache-hit` reads cache reads over input, cache writes and cache reads, and the rows match `GET <api>/api/usage/projects/<id>` and `select sum(input_tokens), sum(output_tokens), sum(cache_write_tokens), sum(cache_read_tokens) from run_usage`. Click `usage-window-7d`: the request gains `?since=`. A project with no runs shows `usage-empty`.
- **Devices (`psettings-devices`).** As the owner open Settings, then `settings-nav-devices`, then click `devices-generate`: `devices-code` shows a code such as `DLVA-275Z` and `devices-code-countdown` reads `Expires in 9:59` and counts down. In a new tab open `http://<lan-ip>:<serverPort>/`, which shows the pairing screen (`shell-pairing`); enter the code and a name and submit. In the owner's tab, within about five seconds, `devices-paired-notice` reads `<name> is paired.` and `device-row` lists it with `Last seen just now`. On the paired tab `fetch('/api/auth/me')` answers `{"kind":"device"}`, Settings has no Devices entry and `fetch('/api/auth/devices')` answers 403. Click `device-revoke`, then `confirm-dialog-confirm`: the row goes, `GET <api>/api/auth/devices` is empty, and the paired tab shows the pairing screen again within a few seconds.
- **Proof.** Screenshots of every section, Threads & permissions with the full-access note and its question, the memory editor with the file list and updated dates, the changed-file notice, the 409 message on the repository row, the Usage totals next to the API response and the DB sums, the empty state, the pairing code with its countdown, the device row on the owner tab and the pairing screen on the revoked tab; `read_console_messages` with `onlyErrors: true` after each flow. State that the runtime was the fake CLI.

## Gotchas

- Screenshots from the Claude in Chrome tab show only the top-left 1164×648 device pixels of a 1280×713 window at a device pixel ratio of 1.1, so the right edge and the bottom of the page are cut off (the Settings tab in a project's header is one casualty). Click coordinates are the screenshot's divided by 1.1. To see the whole page, shrink `#root`: `r=document.getElementById('root'); r.style.transformOrigin='0 0'; r.style.transform='scale(0.85)'; r.style.width='1235px'; r.style.height='680px'`. Reload before clicking again.
- The dialog's right column (`project-settings-pane`) is the scroll box, so Memory's request field sticks to its bottom. It is re-mounted per section, so a section opens at its top.
- A shell inside an AOP thread has `NODE_ENV=production`; a stack started with it refuses every browser write through the dev dashboard with 403 `cross-origin requests are not allowed`. Start the stack with `NODE_ENV` unset.
- `type` acts on whichever element has focus when it runs. Focus the field in a `javascript_tool` step first, put both steps in one `browser_batch` (calls made in parallel run in any order, and the text is lost), and leave a moment after `scrollIntoView` before typing.
- A `find` ref click does not always land: it missed radios and small buttons that were below the fold. Use `scroll_to` first, click by coordinates, or `.click()` the element in `javascript_tool`. Arrow keys inside a Radix select send one step per call; open a select by focusing its trigger and pressing Return.
- `document.dispatchEvent(new Event('visibilitychange'))` does nothing in a tab Chrome reports as hidden (another tab is in front). Use a stream event, as the memory recipe does.
- The tab group can hold other agents' tabs. Close only the tabs you opened.
- A timestamp in the list is rendered in the browser's time zone (`Updated Sep 30, 2026, 3:44 AM` for `2026-09-30T07:44:22.993Z` in New York); compare against the `datetime` attribute, which is the API value.
